# 設計メモ

このアプリを作るときに検討したことと、判断の根拠にした実測値をまとめます。
環境はすべて Apple M1（メモリ 16GB）、モデルは `plamo-3-translate-8b` Q4_K_M です。

## 目標

- 論文を外部へ送らず、手元の Mac だけで翻訳する
- 翻訳に 10 分以上かかる前提で、待ち時間と中断に耐える
- 翻訳を読むだけでなく、原文の図表や数式をすぐ確認できる
- 使っていないときはマシンに負荷をかけない

## 技術選定: FastAPI を選んだ理由

検討の出発点は「FastAPI より Rust のほうが速いのでは」という疑問でした。感覚で決めず、処理時間と CPU 使用率を測りました。

| 処理（15 ページの論文） | 実測 |
| --- | --- |
| PDF のテキスト抽出 | 0.115 秒 |
| 全ページの画像化 | 0.23 秒 |
| LLM による翻訳 | 約 480 秒 |

| プロセス | CPU | メモリ |
| --- | --- | --- |
| Python 側のストリーム受信と JSON 解析 | 1 コアの 0.26% | |
| FastAPI のアイドル時 | 0.2% | 47MB |
| `llama serve` の翻訳中 | 1 コアの約 60%（GPU 51%） | 4.9GB |

処理時間のほぼすべてを LLM の生成が占め、推論はもともと C/C++ の llama.cpp が担当しています。
Rust に置き換えて削れるのは 0.26% のうちの一部だけで、体感は変わりません。
一方で、最も試行錯誤が多い PDF 解析は Python のほうが速く回せます。

効果があったのは言語の変更ではなく、モデルを常駐させないことでした。
llama.cpp は翻訳時だけ起動し、終了 60 秒後に止めます。再読み込みは約 5 秒なので、普段は約 5GB のメモリを解放できます。

## PDF 解析

PDF は「読む順に並んだ文章」ではなく、「座標に置かれた文字」です。次の順で論文の構造を復元します。

1. 画像、描画のまとまり、表を集めて、図表の領域を取ります。
2. 文字サイズとベースラインの差から、添字を `d_k` や `W^O` の形に復元します。脚注番号と区別するため、数学フォントかどうかも見ます。
3. 重なって配置された小さな行を `1/√d_k` にまとめ、添字で分断されたブロックを同じ行に戻します。
4. 回転した arXiv の透かし、ページ番号、複数ページで繰り返すヘッダーを除きます。
5. 全幅のブロックを区切りに、その間を左段、右段の順に並べて読み順を決めます。
6. タイトル、見出し、キャプション、脚注、数式、参考文献を判定します。
7. 文末で終わらない段落は図やページをまたいで次の段落と結合します。

### 図表はキャプションを起点に切り出す

最初は検出した領域をそのまま切り出しましたが、精度が足りませんでした。

- 描画領域が実際より大きく、キャプションに食い込む
- 左右に並ぶ 2 つの表が 1 つの表として検出される
- 図の外に置かれたラベルや軸の目盛りが欠ける

そこで、キャプションの隣から最も近い本文までを図の範囲とする方式に変えました。
キャプションが表の上にあるか下にあるかは論文ごとに揃っているので、論文全体の多数決で決めます。

### 参考文献の分割

参考文献は 1 行ごとにブロックが分かれて抽出されます。番号形式は `[n]` で、著者年形式は字下げで区切りを判定します。
Attention は 40 件、BERT は 56 件に分かれ、PDF 内の引用リンクの宛先の数と一致しました。

## 翻訳

PLaMo 翻訳モデルはチャットテンプレートの引数で言語、文体、用語集を受け取ります。
同じ 9 段落で、用語集と文脈の渡し方を比較しました。

| 条件 | 時間 | シーケンス / 系列 |
| --- | --- | --- |
| 用語集なし、履歴 2 段落 | 105 秒 | 7 / 4 |
| 用語集あり、履歴 2 段落 | 109 秒 | 0 / 11 |
| 用語集あり、履歴 1 段落 | 101 秒 | 0 / 11 |
| 用語集あり、履歴なし | 89 秒 | 0 / 11 |
| 用語集あり、履歴 2 段落を 3 段落ごとに更新 | 104 秒 | 0 / 11 |

（この比較のときは「系列」に統一していました。）

用語集があれば、履歴を渡しても対象の語の揃い方は変わらず、入力処理の分だけ遅くなりました。
そのため履歴なしを標準にしました。論文全体の翻訳は 954 秒から 747 秒に縮みました。
ただし用語集にない語は揺れることがあり、9 段落での比較なので一般化はできません。

## llama.cpp のチューニング

同じ 9 段落を各設定で翻訳し、速度とメモリ、基準の出力との一致を比べました。温度は 0 です。

| 8B の設定 | 9 段落の時間 | 生成速度 | 基準との一致 |
| --- | --- | --- | --- |
| 基準 | 96 秒 | 9.5 トークン/秒 | 9/9 |
| Flash Attention を明示 | 101 秒 | 9.0 トークン/秒 | 9/9 |
| 投機的デコーディング（下書き 4） | 59 秒 | 17.3 トークン/秒 | 9/9 |
| 投機的デコーディング（下書き 5） | 59 秒 | 17.9 トークン/秒 | 9/9 |
| 投機的デコーディング（下書き 6） | 56 秒 | 18.7 トークン/秒 | 9/9 |
| 投機的デコーディング（下書き 8） | 66 秒 | 15.4 トークン/秒 | 9/9 |

KV キャッシュの量子化、バッチサイズ、スレッド数、コンテキスト長の差は計測の揺れの範囲でした。n-gram 方式の投機的デコーディングでは、下書きが 1 件も生成されませんでした。

効いたのは、0.8B を下書きに使う投機的デコーディングだけでした。翻訳は次の語を予測しやすく、下書きの 6 割ほどが採用されます。下書きを増やしすぎると、捨てる分の無駄が上回ります。

論文全体の翻訳は 747 秒から 478 秒に縮みました。

0.8B はどの設定でも約 100 トークン/秒で、差は計測の揺れの範囲でした。KV キャッシュの量子化は出力が変わるので使いません。既定の設定のまま、全文を 79 秒で翻訳します。ただし 8B とは訳文が異なり、比較した 9 段落で一致したものはありません。

翻訳が繰り返しに陥っても止まるように、出力の上限を原文の長さから決めています。上限で止まった段落は失敗として記録し、ジョブは続けます。

## UI

### オフライン

CDN を使わず、KaTeX も同梱しています。原文の表示も PDF.js を使わず、サーバーで画像にしたページを返します。
ビルド工程もありません。

### 数式の表示

翻訳モデルには TeX を渡さず、`d_k` のような平文の形で本文に残します。この形なら翻訳後もほぼそのまま残ることを確認しました。
表示の直前に TeX へ変換し、KaTeX で組版します。`step_num` のように下線を含む識別子は数式にしません。

1 文字の変数は、英字というだけでは判別できません。そこで、PDF で数式用イタリックのフォントが使われた文字を段落ごとに記録し、訳文で同じ文字が単独で現れたときだけ数式にします。実数の `ℝ` も、黒板太字のフォントから判別します。

### スクロールの追従

段落ごとの原文と訳文の位置を対応点にして、その間を線形補間します。
触っている側だけを基準にして、追従した側のスクロールで往復しないようにしています。
Attention では、対応する段落のずれはおおむね 0〜20px、最大で約 70px でした。

### ハイライト

クリックで移動したときは移動先だけを強調し、読み手がスクロールすると 1.6 秒かけて消します。
移動による自動スクロールでは消えないように、移動直後の約 1.2 秒は区別しています。

## 検証

- PDF 解析、翻訳ジョブ、API は pytest、数式の変換は Node のテストランナーで確認します。
- 翻訳サーバーは偽物に差し替えられるので、テストにモデルは不要です。
- 図の切り抜きは切り出した画像を一覧にして目視で確認しました。
- UI は Playwright で PC 幅とスマートフォン幅の操作を確認しました。
